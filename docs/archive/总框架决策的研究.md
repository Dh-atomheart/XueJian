### 结论

我最推荐的可实现组合是：**Tauri 2 + React/TypeScript + Rust 本地核心 + Python sidecar + SQLite/FTS5 + LanceDB + Docling + PyMuPDF + PDF.js + LiteLLM + PydanticAI + LangGraph + FSRS + Manim**。原因很简单：Tauri 官方支持任意前端框架、单代码库跨平台，并且允许把 Python 可执行/API server 作为 sidecar 一起打包；Electron 当然也成熟，但它把 Chromium 和 Node.js 一起嵌进应用，更适合“纯 JS 团队先快做出来”，不太像你这个以本地优先、文档锚点、复习调度为核心的长期产品。 ([Tauri](https://v2.tauri.app/?utm_source=chatgpt.com "Tauri 2.0 | Tauri"))

这类产品不适合“全栈单语言一把梭”。你的需求里同时有三类负载：高交互的桌面/PDF UI、强一致的本地数据与复习调度、以及耗时且易失败的 LLM/视频/音频作业。LiteLLM 提供统一的 OpenAI 格式接口到 100+ provider；PydanticAI 非常适合结构化输出和校验；LangGraph 则适合长运行、可恢复、human-in-the-loop 的 Agent 工作流。 ([LiteLLM](https://docs.litellm.ai/docs/?utm_source=chatgpt.com "Getting Started | liteLLM"))

我会把系统理解成四层：**桌面壳/视图层（Tauri + React + PDF.js）→ 本地核心（Rust + SQLite/FTS5 + FSRS）→ AI 工作进程（Python + Docling + PyMuPDF + LiteLLM + PydanticAI/LangGraph + Manim）→ 派生索引（LanceDB + graph index）**。

核心实体建议一开始就定死：`Document`、`Page`、`SourceAnchor`、`Card`、`CardGroup`、`Cluster`、`ReviewState`、`StudyEvent`、`Artifact`。其中 **CardGroup** 是模型建议的语义组，**Cluster** 是用户主导的上层簇；模型可以建议，但不要替用户自动改簇。

### 按你的 11 个需求逐项落地

1. **PDF → 闪卡生成、分组、手工增删改、导出**  
    文档解析我会用 **Docling + PyMuPDF**：Docling 的 `DoclingDocument` 能保留 document hierarchy、layout bounding boxes 和 provenance；PyMuPDF 负责高性能 PDF 提取/操作与精确页坐标。卡片生成不要直接让模型吐自由文本，而要输出结构化 `CardDraft{title, front, back, anchors[], confidence}`。导出层直接兼容 Anki 的 note/card 思路：Anki 手册把 note 定义为 fields，card 由模板决定正反面；导出支持文本和 `.apkg`，用 genanki 可以直接写出 Anki 包。 ([Docling Project](https://docling-project.github.io/docling/concepts/docling_document/?utm_source=chatgpt.com "Docling Document - Docling"))
    
2. **在 PDF 页面侧边贴“便笺式卡片”**  
    这里的关键不是“把卡片写进 PDF”，而是保存不可变的 **source anchor**：`{doc_id, page, bbox, quote_hash, color}`。PDF.js 官方把 viewer 明确定位成构建自定义 PDF viewer 的良好起点；其页面 API 也能 render、getViewport、getTextContent 和 getAnnotations。交互上非常值得借鉴 Zotero：它的 PDF Reader 有右侧 Notes pane、注释颜色、以及 “Show on Page” 的回链方式，这和你说的“像书页边贴笺”几乎是同一路线。 ([Mozilla GitHub Pages](https://mozilla.github.io/pdf.js/getting_started/?utm_source=chatgpt.com "PDF.js - Getting Started"))
    
3. **本地知识库 + 选中文档问答**  
    我会让 **SQLite 成为 source of truth**，用 **FTS5** 做词法检索，用 **LanceDB** 做语义检索，再加一层 reranker 做 hybrid retrieval。SQLite 官方把 FTS5 定义为全文搜索虚拟表模块；LanceDB 官方把自己定义为 in-process 的 embedded database，AnythingLLM 也默认用 LanceDB 并强调文档文本和 embeddings 不离开应用。产品层再加一个 `Notebook/Workspace` 概念，只对用户勾选的文档集检索与回答，这一点可直接参考 Open Notebook 的 notebooks / sources / chat 组织方式。 ([SQLite](https://sqlite.org/fts5.html?utm_source=chatgpt.com "SQLite FTS5 Extension"))
    

嵌入模型默认我会优先 **BGE-M3**，因为它同时覆盖 dense / sparse / multi-vector，支持 100+ 语言和长文档；如果你的 PDF 常有表格、图表、插图，再升级到 **jina-embeddings-v4** 这种面向 visually rich document retrieval 的模型。 ([Hugging Face](https://huggingface.co/BAAI/bge-m3?utm_source=chatgpt.com "BAAI/bge-m3 · Hugging Face"))

4. **卡片结构：标题 + 正面 + 背面**  
    我不建议只存两个字符串。更合适的是：`title + front + back + anchors + tags + group_id + cluster_id + card_type + export_guid`。其中 `front/back` 直接贴合 Anki 的 Front/Back 语义，`title` 负责浏览与搜索；Anki 的文档也说明了 note 的 fields 与 card templates 是分离的，这正好适配你的“用户手动改卡片，但导出结构仍稳定”的需求。 ([Anki Manual](https://docs.ankiweb.net/getting-started.html "https://docs.ankiweb.net/getting-started.html"))
    
5. **Agent 驱动的演示动画生成器**  
    这部分最优路线就是 **Manim**。Manim Community Edition 是 MIT 许可、社区维护的开源项目，官方也明确把它定位为 explanatory math videos / precise programmatic animations 的引擎。工程上不要让 Agent 直接“写脚本然后在主进程执行”，而是做成流水线：`retrieve anchors -> 诊断难点 -> storyboard -> manim script -> 沙箱渲染 mp4 -> 预览 -> 用户可回改再渲染`。 ([Manim Community](https://www.manim.community/ "https://www.manim.community/"))
    
6. **像 NotebookLM 那样生成 AI 播客**  
    工作流上我会直接借鉴 **Open Notebook** 的 `notebook -> sources -> chat -> transformations -> podcasts` 形态；开源流水线可参考 **Podcastfy** 和 **podcast-creator**，后者已经把 `outline -> transcript -> audio` 组织成 LangGraph workflow。产品设计上，建议把“检索与写稿”固定在本地 agent 流里，而把“音频合成”做成 provider adapter：首版先接 BYOK 的云 TTS，后续再补本地 TTS。 ([GitHub](https://github.com/lfnovo/open-notebook "https://github.com/lfnovo/open-notebook"))
    
7. **学习安排、复习间隔、推荐今日该学什么**  
    这块不要自己重新发明算法，直接上 **FSRS**。Anki 已经把 FSRS 作为正式选项，且明确说明它比旧的 SM-2 更能估计遗忘、在相同时间里记住更多；工程上如果核心在 Rust 就用 `fsrs-rs`，如果排期更偏 Python worker 就用 `py-fsrs`。界面层只暴露“今日推荐、预估负荷、目标保留率”，不要把算法参数塞给普通用户。 ([Anki Manual](https://docs.ankiweb.net/deck-options.html?highlight=FSRS "https://docs.ankiweb.net/deck-options.html?highlight=FSRS"))
    
8. **学习分析、GitHub 式热力图、学习时长统计**  
    所有 review / study / edit / export / ask / animation / podcast 都应该写成 **event log**，再聚合出日历热力图、总学习时长、完成率、延期率、复习负荷、留存趋势。图表层我会用 **Apache ECharts**，因为它支持 responsive design，同时还有自动图表描述和 decal patterns 这类无障碍能力，比较适合学习数据面板。 ([Apache ECharts](https://echarts.apache.org/en/index.html "https://echarts.apache.org/en/index.html"))
    
9. **BYOK：兼容 OpenAI 和 Anthropic**  
    这一层要做成 **provider registry / adapter**，不要把 “OpenAI-compatible” 当成唯一协议。Open Notebook 的 “Add Credential → Test Connection → Discover/Register Models” 很值得借鉴；Open WebUI 也证明了 Anthropic 可以挂在 OpenAI-compatible 入口上。但 Anthropic 官方文档写得很清楚：它的 OpenAI SDK compatibility 主要用于测试/比较，不是大多数生产场景的长期方案，而且完整的 Claude 能力（如 PDF processing、citations、extended thinking、prompt caching）应该走原生 Claude API。密钥存储则不要学 web app 写 `.env`，桌面端至少放进 Tauri Stronghold；要更贴近系统体验，再接平台 keychain/keyring。 ([GitHub](https://github.com/lfnovo/open-notebook/blob/main/docs/5-CONFIGURATION/ai-providers.md "https://github.com/lfnovo/open-notebook/blob/main/docs/5-CONFIGURATION/ai-providers.md"))
