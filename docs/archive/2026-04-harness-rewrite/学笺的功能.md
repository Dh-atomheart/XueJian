> 当前 AI 编排、跨端约束与模块边界以 [ai-architecture-decision.md](./ai-architecture-decision.md) 和 [spec.md](./spec.md) 为准。

此APP用来解决需要重复性记忆某知识，例如考研考公，期末备考情况。为用户提供可视化知识学习记忆情况，在ai大模型驱动下助力用户学习记忆。

## 主要功能：

1. 可以实现将用户上传的文档（真PDF，markdown文档，doc文档，TXT等）通过大模型或者某些工具帮助下输入的内容转化为类似anki卡片（flash卡片），相似内容的卡片是一组的，不同的组又可以组合成同一簇（这一步是用户实现的）。此外，用户可以手动增加卡片，删除卡片，修改卡片。甚至导出卡片。

2. 当用户输入的文档生成了卡片后，当用户打开这些文档并且进行查看时这些卡片可以在一侧显示出来，呃，比如说某一张卡片，它是根据某某页生成的，所以这个卡片就显示在某某页的一侧。这一功能的实现就如同真的像是在真实的书里贴上笺一样。

3. 上传的文档，可以构成用户的本地知识库，可以实现选取相应的文档进行ai问答，ai会根据选取的文档中的内容进行回复。

4. 卡片的结构应当是标题+内容。更详细的说应该是：卡片正面显示的是问题（或者是内容的简要描述等）；卡片背面显示的是内容。

5. 可以实现讲某个卡片内容进行可交互式的转化，比如某个数学知识，可以点击生成演示动画，llm可以使用manim或者p5.js等其他工具生成，并且可以预览。

6. 可以根据输入的文档生成对应内容的提示词可以生成对应的AI播客，像NoteBookLM那样的。agent会先检索知识库内容，并且编写对话稿，最后生成对话。

7. 可以实现学习卡片的安排，每日学习什么，应该学那些东西，AI 或者算法会推荐最应该学习的卡片，以及学习过的卡片复习间隔与周期，从而让用户达到复习和记忆某个知识点的能力（类似anki的 FSRS，用户上手就用，用户不关注背后的实现逻辑）

8. 方便用户查看自己学习的情况，比如每日学习记录，类似github主页那样的组件，以及总学习时长等等可视化的图形预览。

9. 采用BYOK策略，用户可以自由的使用自己开通的大模型API Key。兼容openai 以及anthropic协议。

10. 引入知识图谱，方便用户查过自己的知识体系以及帮助大模型进行更高质量的生成。

11. 绘制良好、简洁并且对用户友好的用户界面，加入手绘风格的组件等。

12. 加入积分系统，激励用户持续学习。

13. 开发windows桌面端以及安卓手机app。


## 总体可实现性评估

整体可实现性评分：

**完整版（按你列出的 13 项全部都要做，并且要做成一个可用、开源、跨端产品）：4.1/5**  
**核心闭环（1/3/4/7/8/9 + 基础 UI）：4.8/5**

判断依据很直接：你这个项目需要的底层拼图基本都已经存在，不属于“科研级不可落地”，更像“复杂工程集成”。PDF 侧有 PDF.js；Windows/Android 跨端有 Tauri 2；OpenAI 和 Anthropic 都有成熟的消息式/结构化/工具调用接口；FSRS 也已有开源实现；知识图谱与 GraphRAG 路线也有现成技术栈支撑。([Mozilla GitHub Pages](https://mozilla.github.io/pdf.js/?utm_source=chatgpt.com "PDF.js - Home"))

分项评分：

1. **文档转卡片、分组、簇化、编辑、导出：4.5/5**  
    可做，而且是比较成熟的一类能力。难点不在“生成卡片”，而在去重、合并、组/簇一致性、以及批量编辑体验。OpenAI 的 Structured Outputs 和 Anthropic 的 Messages/tool use 都适合把卡片结构稳定落成 schema。([OpenAI Platform](https://platform.openai.com/docs/guides/structured-outputs?api-mode=&utm_source=chatgpt.com "Structured model outputs | OpenAI API"))
    
2. **文档侧边贴笺式卡片展示：4/5**  
    可做，且 PDF 场景可行性很高。PDF.js 本身就是 Web 标准的 PDF 解析与渲染平台。真正拉难度的是“卡片稳定锚定到页码/段落/坐标”，以及缩放、重排、不同文档格式下的一致体验。PDF 最容易，DOC/DOCX 次之。([Mozilla GitHub Pages](https://mozilla.github.io/pdf.js/?utm_source=chatgpt.com "PDF.js - Home"))
    
3. **本地知识库 + 选中文档问答：4.5/5**  
    这是标准 RAG 形态，工程上成熟。难点主要是分块、引用回溯、增量索引、本地缓存和命中文档范围控制，不在“能不能做”。
    
4. **卡片结构为正反面：5/5**  
    几乎没有技术风险，就是标准数据建模与交互设计问题。
    
5. **卡片内容转可交互演示动画：3/5**  
    能做，但这是明显的高波动模块。p5.js 适合前端交互式可视化，Manim 适合数学动画；难点在于让 LLM 稳定生成“可运行、可解释、可预览、可控”的代码与动画，而不是只生成一段看起来像代码的文本。([p5.js](https://p5js.org/?utm_source=chatgpt.com "p5.js"))
    
6. **从知识库生成 AI 播客：3.5/5**  
    可做，但要做到接近 NotebookLM 那种自然度、信息密度和双人对话感，难度明显上升。脚本生成不难，难的是长文档覆盖、对话节奏、说话风格稳定、成本控制。现成语音链路已经具备：OpenAI 官方文档明确支持 speech-to-speech，或者 STT→LLM→TTS 的链式方案，也提供 TTS 接口。([OpenAI Platform](https://platform.openai.com/docs/guides/audio?_bhlid=baea7a1bd3443b827b57b9b8e34cdd96887112c9&utm_beehiiv=email&utm_source=chatgpt.com "Audio and speech | OpenAI API"))
    
7. **学习安排、复习周期、最该学什么（FSRS 类）：4.5/5**  
    这块很可做，因为 FSRS 已经是成熟开源路线，而且有多语言实现，不需要你从零发明调度器。真正的难点是冷启动、用户无感上手、以及卡片粒度不均导致的调度误差。([GitHub](https://github.com/open-spaced-repetition?utm_source=chatgpt.com "Open Spaced Repetition - GitHub"))
    
8. **学习记录与可视化：4.5/5**  
    工程上比较常规，核心是埋点模型、统计口径和展示设计，不是技术阻塞项。
    
9. **BYOK，兼容 OpenAI / Anthropic：4/5**  
    可做，而且值得做。OpenAI 这边有 Responses API 与结构化输出；Anthropic 这边有 Messages API 与 tool use。真正的复杂度在协议抽象层、错误处理、速率限制、账单提示、模型能力差异和兼容性测试。([OpenAI Platform](https://platform.openai.com/docs/guides/structured-outputs?api-mode=&utm_source=chatgpt.com "Structured model outputs | OpenAI API"))
    
10. **知识图谱：3.5/5**  
    不是做不出来，而是“做出来且真的提升体验”更难。Neo4j 已经有 Knowledge Graph Builder、GraphRAG 等路线，说明技术方向成熟；但实体抽取、实体消歧、关系质量、增量更新、可解释性会持续吞工程时间。([Graph Database & Analytics](https://neo4j.com/blog/developer/rag-tutorial/?utm_source=chatgpt.com "Using a Knowledge Graph to implement a RAG application"))
    
11. **简洁、手绘风 UI：4/5**  
    完全可实现。主要是设计与前端打磨成本，不是技术可行性问题。
    
12. **积分系统：5/5**  
    技术上最容易的一类。真正要小心的是防刷分和激励机制设计，而不是实现本身。
    
13. **Windows 桌面端 + 安卓 App：3.5/5**  
    能覆盖，但会明显抬高整体复杂度。Tauri 2 官方已经支持桌面和移动平台，包含 Windows 与 Android，所以“单代码库覆盖两端”这件事本身成立。真正难的是文件系统差异、WebView 行为差异、离线缓存、上传预览、音频生成链路和端侧资源约束。([Tauri](https://v2.tauri.app/?utm_source=chatgpt.com "Tauri 2.0 | Tauri"))
    

**结论：**  
从“纯工程可实现性”看，**学笺是一个明显可做成的开源 Agent 应用**。  
拉低总分的不是 1/3/4/7/8/9 这些核心能力，而是 **2（贴笺式文档锚定）、5（交互式动画生成）、6（AI 播客质感）、10（知识图谱质量）、13（双端一致性）**。  
所以我的最终评分是：**4.1/5**。


## 简略的技术选型以及规格文档

### 技术选型建议

1. **文档处理与卡片生成：**
    
    - **PDF**：使用 **PDF.js** 处理 PDF 文件，提取文档内容并生成卡片。它是一个成熟的 JavaScript 库，能够支持不同格式的 PDF 文件。
        
    - **Markdown/Doc/TXT 文档**：使用 **marked.js** 解析 Markdown 文件，**python-docx** 或 **pandoc** 处理 DOC 文件，**Python** 标准库处理 TXT 文件。
        
    - **AI 文本生成**：OpenAI GPT 或 Anthropic LLM 用于卡片内容的生成，支持从文本中提炼出问题和答案对。
        
2. **UI设计与卡片展示：**
    
    - **前端框架**：使用 **React** 或 **Vue.js**，搭配 **Tailwind CSS** 进行布局和样式设计，确保可视化效果和用户交互流畅。
        
    - **PDF 界面**：使用 **PDF.js** 实现文档渲染和与生成的卡片内容关联，用户可以在一侧显示卡片，增强交互体验。
        
3. **学习进度与推荐系统：**
    
    - **学习进度**：实现类似 **FSRS** 的复习算法，参考 **Spaced Repetition** 技术，使用 Python 进行模型计算。
        
    - **推荐系统**：结合 **Scikit-learn** 或 **TensorFlow** 的基础算法，根据用户学习进度推荐卡片内容。
        
4. **AI问答与知识库构建：**
    
    - **文档检索与问答**：使用 **FAISS**（Facebook AI Similarity Search）进行高效的向量数据库检索，结合 **OpenAI GPT** 或 **Anthropic LLM** 进行答案生成，基于用户选定文档作为上下文。
        
5. **动画生成与交互式功能：**
    
    - **数学动画**：集成 **Manim** 或 **p5.js**，以生成动画演示数学或其他知识点的概念。Manim 适用于数学公式，p5.js 可以实现动态交互效果。
        
6. **播客生成：**
    
    - **AI 播客**：使用 **OpenAI GPT** 或 **Anthropic LLM** 生成对话脚本，再配合 **TTS（Text-to-Speech）** 生成语音内容，播客音频生成工具可以集成 **Google TTS** 或 **AWS Polly**。
        
7. **跨平台开发：**
    
    - **桌面端**：使用 **Tauri** 或 **Electron** 开发桌面端应用，支持 Windows 和 Linux。
        
    - **移动端**：使用 **Flutter** 或 **React Native**，实现跨平台开发，支持 Android 和 iOS。

- 功能实现：
    
    - 学习进度：记录用户学习卡片的状态（未学、学习中、已掌握）。

#### 4. **AI问答与知识库模块**

- 功能：通过 AI 引擎回答用户关于文档内容的问题。
    
- 技术：**FAISS**, **OpenAI GPT** 或 **Anthropic LLM**。
    
- 功能实现：
    
    - 知识库构建：根据上传文档创建本地知识库。

- 技术：**OpenAI GPT**, **TTS**（Google TTS, AWS Polly）。
    
- 功能实现：
    
    - 脚本生成：生成符合播客风格的对话脚本。
        
    - 语音生成：将脚本转化为语音播客内容。
        

#### 7. **积分与激励系统模块**

- 功能：根据用户学习进度给予积分，并显示用户的学习成就。
    
- 技术：**React/Vue.js** + **Backend (Node.js/Python)**。
    
- 功能实现：
    
    - 积分系统：根据学习卡片数量、学习时长等因素分配积分。
        
    - 激励机制：通过积分系统激励用户持续学习。
        

#### 8. **跨平台应用模块**

- 功能：支持桌面和移动端跨平台应用。

## 基于测试驱动的应用开发

基于测试驱动开发 (TDD) 的方法有助于确保系统的稳定性与功能性，特别是在涉及复杂 AI 技术的应用开发时。对于“学笺”应用，以下是针对各个模块的测试标准与测试方案。

### 1. **文档上传与处理模块**

#### 测试目标：

确保文档格式（PDF、Markdown、DOCX、TXT）能够正确解析并生成学习卡片。

#### 测试标准：

- **文档上传**：测试上传功能，确保不同格式的文档（PDF、Markdown、DOCX、TXT）能正确上传，且不会丢失数据。
    
- **文档解析**：确保每种格式的文档能够被正确解析，且提取的文本内容没有遗漏。
    
- **卡片生成**：确保解析后的内容能够转化为卡片，并且内容的正反面能够正确生成。
    

#### 测试方案：

- **单元测试**：
    
    - 编写针对每种文档格式解析的单元测试。
        
    - 使用 mock 数据模拟文档上传与解析，确保不同格式能正确解析。
        
    - 编写单元测试来验证从文档中提取的文本内容与卡片生成逻辑。
        
- **集成测试**：
    
    - 上传包含不同内容的测试文档，验证卡片内容的生成。
        
    - 对比上传的文档内容与生成卡片的内容，确保匹配无误。
        
- **UI 测试**：
    
    - 测试文档上传功能的交互行为，确保用户界面友好，文档上传成功后卡片自动生成。
        

#### 示例：

- 测试上传 PDF 文件后，卡片是否正确生成。
    
- 测试上传 Markdown 文档后，文档内容是否被提取并正确生成卡片。
    

### 2. **卡片管理模块**

#### 测试目标：

确保用户能够正确地管理卡片，包括查看、编辑、删除和导出。

#### 测试标准：

- **卡片展示**：确保卡片能够在 UI 中正确显示，且能够切换显示正面和背面。
    
- **卡片编辑**：确保用户能够正确编辑卡片内容，且修改后的内容能够被保存。
    
- **卡片删除**：确保用户删除卡片后，卡片从系统中消失。
    
- **卡片导出**：确保卡片能够导出为 CSV 或其他支持的格式。
    

#### 测试方案：

- **单元测试**：
    
    - 对卡片数据结构的增删改查（CRUD）操作进行单元测试，确保卡片操作的正确性。
        
    - 编写验证卡片导出功能的测试，确保导出的格式符合预期。
        
- **集成测试**：
    
    - 上传文档并生成卡片后，测试编辑、删除和导出的功能是否如预期工作。
        
- **UI 测试**：
    
    - 使用自动化测试工具（如 Selenium 或 Cypress）进行卡片的显示、编辑、删除、导出等操作，确保用户能够顺利完成操作。
        

#### 示例：

- 测试创建新卡片后，是否能正确显示卡片内容。
    
- 测试编辑卡片后，修改的内容是否正确保存。
