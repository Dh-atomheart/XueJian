# 学笺项目整改与增强计划

> 文档版本：v1.1  
> 编制日期：2026-04-24  
> 适用范围：学笺项目 v0.1.0 -> v0.2.0 升级路径  
> 文档定位：基于当前仓库代码真相，对既有方案做优先级重排、现状纠偏与实施收敛

## 一、修订结论

本轮不是从零规划一个新产品，而是把当前仓库中已经存在的实现、未完成的补洞项和中长期增强项重新排序，形成一份可执行的整改计划。

总体判断如下：

- 原方案的大方向基本合理，仍然围绕“文档导入 -> 卡片生成 -> 间隔复习 -> 问答/图谱 -> 播客/动画”构建本地优先学习闭环。
- 原方案最大的问题不是方向错误，而是**没有充分对齐代码现状**，把不少“已有骨架或初版能力”的模块写成了“完全空白”。
- 里程碑 1 明显过载，既混入了阻塞性的安全整改，也混入了中期增强和技术预研，导致优先级失真。
- 后续实施应从“全新能力立项”改为“现有能力补齐 + 风险优先整改 + 谨慎扩展”。

本次修订采用以下原则：

- 先修正文档中的现状误判。
- 先做阻塞用户闭环和安全边界的工作。
- 现有 DTO、状态机、网关接口尽量不大改，优先做增量增强。
- 未充分验证的技术选型保留为候选路径，不写成既定事实。


## 二、现状纠偏

### 2.1 卡片生成引擎（Card Generation Pipeline）

**现状评估**

卡片系统 V2 的“候选 -> 审核 -> 正式”主线是正确的，现有实现已经具备卡片生成工作流基础，但仍缺少三个关键补洞：

- PDF 类型分流仍不完整，未把原生文本 PDF、扫描 PDF、混合 PDF 明确区分。
- 文档分块虽已有结构化基础，但还没有作为正式的“语义分块策略”收敛为统一能力。
- LLM 输出质量缺少更严格的 schema 校验、最低质量门槛和来源页绑定约束。

**整改目标**

- 保留现有候选卡片审核流，不改成“模型直接正式入库”。
- 增加 PDF 解析分流、语义分块、来源页绑定和卡片输出校验。
- 自动聚类保留为增强项，不进入首批阻塞交付。

**建议改进**

**1. 增加 PDFTypeDetector 预处理层**

- 在执行解析前判断 PDF 是否存在可提取文本层。
- 有文本层时优先走 PyMuPDF；无文本层时走 Docling OCR；混合型 PDF 按页分流。
- Docling OCR 保持为可配置能力，不把具体 OCR 引擎写死到业务逻辑中。
- 难度预估：中等（3-4 人天）

**2. 引入正式的 SemanticChunker 语义分块策略**

- 基于标题层级、段落边界、表格边界和现有 `hierarchyPath/pageStart/pageEnd` 进行结构化分块。
- 输出必须稳定保留来源页、层级路径和 chunk 与 section 的映射。
- 难度预估：中等（3-4 人天）

**3. 增加 LLM 输出 Schema 约束与异常兜底**

- 模型输出统一为结构化 JSON，而不是自由文本拼接。
- Python 侧使用 Pydantic 做严格校验，过滤空卡片、过短卡片和缺少来源绑定的卡片。
- 相似度阈值、最小词数等门槛应作为可调参数，不在文档中写死为唯一标准。
- 难度预估：简单（2-3 人天）

**4. CardClusterer 调整为增强项**

- 自动归类与聚类建议保留，但不再作为里程碑 1 必做项。
- 该能力在审核效率足够成为真实瓶颈后再推进。
- 难度预估：中等（3-5 人天）

**文件落点建议**

- `xuejian/orchestration_service/parsing/docling_pipeline.py`
- `xuejian/orchestration_service/workflows/card_generation.py`


### 2.2 本地知识库对话（RAG / GraphRAG 问答）

**现状评估**

该模块不是“仅有向量相似度匹配”。当前代码已经具备：

- FTS5 检索回退
- `search_hybrid` 混合检索骨架
- `graph_rag_search` 图增强检索入口
- 回答结构中已有 `citations`

真实问题在于：

- 引用追溯还不够稳定，citation 完整性仍依赖模型输出质量。
- 回答降级策略有骨架，但需要更清晰的契约化行为。
- GraphRAG 存在入口，但不应在当前版本宣称为“完整三层检索体系已规划落地”。

**整改目标**

- 将该模块定位为“补全引用、稳定混检、控制回答质量”。
- 保留 Hybrid + GraphRAG 方向，但把完整版多层推理下调为增强项。

**建议改进**

**1. 先稳定现有 Hybrid 检索链**

- 保留 FTS5 -> Hybrid -> GraphRAG 增强的现有方向。
- M1 重点不是新建“三层检索架构”，而是让现有链路在依赖缺失时稳定降级。
- 难度预估：中等（3-4 人天）

**2. 引入引用溯源强制机制**

- 后端对返回给前端的每个 citation 强制补齐最小字段：`chunkId`、`documentId`、`page`。
- 页码和 chunk 绑定由后端保证，不依赖 LLM 自觉生成。
- 前端继续用页码跳转与 PDF 高亮联动做展示。
- 难度预估：中等（3-4 人天）

**3. 明确回答降级策略**

- 无法检索到足够内容时返回明确 no-answer / no-relevant-content。
- GraphRAG、embedding、provider 失效时必须自动回退到 FTS5 / excerpt 模式。
- 该策略应写入公共契约和测试口径。
- 难度预估：简单（2-3 人天）

**4. 对话持久化与反馈保留为次优先增强项**

- 保留对话持久化和“有帮助/有误”反馈设计。
- 不作为 M1 闭环阻塞项。
- 难度预估：简单（2-3 人天）

**文件落点建议**

- `xuejian/orchestration_service/workflows/knowledge_qa.py`
- `xuejian/src-tauri/src/gateway/host_http.rs`


### 2.3 动画能力（Card Animation / Future Manim）

**现状评估**

该模块并非空白。当前仓库已经具备：

- 卡片动画工作流
- 前端动画预览
- LLM 生成脚本 + 规则回退

因此本模块在当前版本中的正确定位应是：

- 短期：增强现有 Framer Motion 脚本体系
- 中期：评估是否引入更强的 Manim / Sidecar 路线

**整改目标**

- 文档不再写“功能完全空白”。
- 文档不再把 `manim-mcp-server` 活跃度表述为既定事实。

**建议改进**

**1. M1 不引入 Manim Sidecar**

- 现阶段先保留现有动画脚本体系。
- 聚焦失败回退、脚本质量、前端预览体验与状态一致性。
- 难度预估：简单（1-2 人天）

**2. M2 评估 Storyboard + Validator 增强**

- 若要引入更复杂的动画生成，应先增加 storyboard 规划和脚本静态检查。
- 这些增强只在现有动画价值被验证后推进。
- 难度预估：中等（3-5 人天）

**3. Manim 路线降级为候选技术**

- Manim 可保留为未来增强路线。
- 在未完成本地打包、沙箱、依赖体积、稳定性验证前，不写成既定交付。

**文件落点建议**

- `xuejian/orchestration_service/workflows/card_animation.py`

### 2.4 FSRS 调度策略

**现状评估**

项目已接入 `ts-fsrs`，FSRS 不是未选型状态。当前真正缺的是：

- 每日学习队列生成
- 复习计划入口
- 提醒与展示收口

**整改目标**

- 以 `ts-fsrs` 承担日常调度计算。
- 不把 Rust / 其他实现升级为主路线，除非后续真的需要参数训练或批量计算优化。

**建议改进**

**1. 以 ts-fsrs 作为日常调度主力**

- 继续在前端或现有 TypeScript 服务层执行常规调度计算。
- Rust 侧仅保留为宿主辅助或后续优化入口，不抢占主架构。
- 难度预估：简单（1-2 人天）

**2. 实现学习日程调度器**

- 基于 `due_at` 与每日上限生成复习队列。
- 将其明确纳入 M1 闭环。
- 难度预估：简单（1-2 人天）

**3. 通知提醒保留为非阻塞增强项**

- 桌面通知可以做，但不应与闭环主线绑定。
- 先完成复习入口和队列，再补提醒体验。
- 难度预估：中等（2-3 人天）

**文件落点建议**

- `xuejian/src/services/`
- `xuejian/src/components/learning/`


### 2.5 AI 播客生成工作流

**现状评估**

该模块不是空白，也不是纯设计态。当前仓库已经具备：

- 播客页面和列表/详情交互
- Rust 宿主命令与仓储
- Python 编排、预算控制、审阅中间态与分段音频存储

因此本模块的正确表述应是“增强现有工作流”，而不是“从零实现播客系统”。

**整改目标**

- 继续以现有播客主线为基础做增强。
- 不在当前版本重做为“多角色声音系统”。

**建议改进**

**1. 保持现有脚本审阅中间态**

- 审阅不是新增能力，而是正式流程的一部分。
- 后续只增强交互与恢复逻辑，不重写状态机。
- 难度预估：简单（1-2 人天）

**2. 多角色播客体系下调到 M2**

- 2 主持 + 1 嘉宾可以作为风格增强方案。
- 在当前版本不作为必须交付，也不应重写现有 schema 作为前置条件。
- 难度预估：中等（3-4 人天）

**3. 分段合成保留为已有方向上的增强**

- 长播客分段 TTS 与拼接方向合理。
- 但应被写成“增强现有拼接链路”，而不是“新增架构”。
- 难度预估：中等（2-3 人天）

**4. Web Speech 回退仅保留为尽力方案**

- `SpeechSynthesis` 在浏览器层面可用，但桌面 WebView 兼容性、语音包和行为一致性不可完全保证。
- 文档只能把它写成“尽力回退”，不能写成稳定离线承诺。
- 难度预估：简单（1-2 人天）

**文件落点建议**

### 2.6 向量存储方案（sqlite-vec 的定位）

**现状评估**

继续使用 `sqlite-vec` 作为本地嵌入式向量能力是合理的，但应避免两个误区：

- 不把它描述成 ANN 引擎。
- 不在没有真实压测的情况下预先承诺固定阈值和迁移时机。

**整改目标**

- 短期继续保留 `sqlite-vec`。
- 先做监控和压测，再决定是否需要 LanceDB 抽象层。

**建议改进**

**1. M1-M2 保持 sqlite-vec**

- 结合 FTS5 做混合检索，继续符合本地优先和单库设计目标。
- 不在当前阶段引入独立向量数据库迁移成本。
- 难度预估：简单（1-2 人天）

**2. 阈值策略从“写死 50,000”改为“基于压测设定”**

- 先记录向量规模、检索延迟、P95 表现和设备差异。
- 在获得真实数据前，不把 50,000 条写成正式阈值。
- 难度预估：简单（1-2 人天）

**3. LanceDB 保留为后续候选路径**

- 仅在压测证明 `sqlite-vec` 成为瓶颈时，再抽象向量后端接口。
- 该项不进入 M1，也不应作为当前承诺。
- 难度预估：中等（3-4 人天）

**文件落点建议**

- `xuejian/src-tauri/src/db/vector_repo.rs`
- `xuejian/orchestration_service/clients/host_gateway.py`


## 三、安全保障体系（阻塞整改项）

### 3.1 API Key 安全存储整改

**现状评估**

仓库已接入 Stronghold 与 SecretStore，不是“仅有接口定义”。但当前实现仍存在明显安全问题：

- 使用硬编码 32 字节 key material 初始化 Stronghold。
- SecretStore 提供直接读回明文 key 的能力。
- 文档与实现之间对“主密码 / 解锁态 / 宿主注入边界”的定义还不一致。

因此该项是**里程碑 1 的首要阻塞整改项**。

**整改目标**

- 使用 Tauri Stronghold 推荐的 Argon2 初始化方式派生 32-byte key material。
- 引入“解锁 vault”的运行时概念。
- 保持前端不可直接读回明文 key。
- 运行时若必须使用密钥，仅允许宿主内部读取并注入请求。

**实施步骤**

**Step 1：重构 SecretStore 初始化**

- 移除硬编码 vault key。
- 改为使用用户主密码或本地受控派生输入，经 Argon2 生成 Stronghold 所需 32-byte key material。
- 明确首次初始化、重复启动、错误恢复的流程。

**Step 2：引入 vault 解锁状态**

- 宿主维护“已解锁/未解锁”运行时状态。
- 前端只能感知状态，不能获得明文 key。
- 允许 UI 提示用户解锁，但不新增“读取 API Key 明文”的公共接口。

**Step 3：收紧明文边界**

- 配置列表接口继续只返回 `hasStoredKey`、`keyStatus`、`keyVerifiedAt` 等元数据。
- 业务运行时由宿主读出密钥并注入 provider 请求，不把明文暴露给前端缓存层。

**Step 4：对齐连接校验状态机**

- `storeApiKey`、`test_api_connection`、`fetch_provider_models` 继续复用现有接口。
- 优先补充测试和状态一致性，而不是重做接口。

**难度预估**

- 中等偏高（4-6 人天）

**文件落点建议**

- `xuejian/src-tauri/src/secrets/`
- `xuejian/src-tauri/src/commands/settings.rs`


### 3.2 Provider 连接校验与容灾

**现状评估**

连接测试、模型发现和工作流分配接口已经存在。当前重点不在于新建命令，而在于：

- 保证验证结果和 `key_status` 一致。
- 统一失败分类。
- 减少文档与实现口径漂移。

**整改目标**

- 让连接测试、模型发现、工作流分配和预算记录成为一套稳定的基线能力。
- 自动切换策略保留，但不作为 M1 阻塞项扩张太多实现面。

**建议改进**

- 连接测试成功时统一更新 `key_status=verified` 和时间戳。
- 连接测试失败时更新为 `invalid` 或保守降回 `stored`，避免状态漂移。
- Provider 不可用提示、失败原因记录和时间戳展示进入 UI。
- 自动降级链可以继续保留，但先以显式告警优先，避免过度隐式切换影响可解释性。


## 四、AI 编排服务边界

### 4.1 当前原则

保持现有“Rust Host + Python orchestration + React + SQLite”的总体边界，不在本轮进行大规模重构。

### 4.2 Agent / Workflow 收敛方向

当前更合适的说法不是“立即建立三大 Agent 新体系”，而是：

- 在现有 workflow 基础上逐步补齐输入/输出契约。
- 把卡片生成、问答、播客、动画的结构化输入输出进一步固定下来。
- 避免在未解决安全、引用和闭环问题前，先引入一套新的 Agent 注册框架。

**实施要点**

- Workflow 之间仍通过 Orchestrator / Host 网关交互。
- 若后续引入 Agent 注册机制，应以现有 workflow 为底座做兼容封装，不破坏现有调用路径。
- 该项不再作为 M1 必交付，而是架构收敛方向。


## 五、前端架构优化：手绘体系收口

**现状评估**

项目已经引入 `roughjs`，且已有 `Sketch*` 组件与设计令牌，不是完全未建设状态。当前问题是：

- 组件分布较散
- 视觉参数和令牌尚未完全统一
- 是否更换底层 renderer 仍缺少必要收益验证

**整改目标**

- 先统一 token 和组件归档。
- 暂不切换到 `react-rough-fiber`，也不再宣称它是 Rough.js 官方 React 渲染器。

**实施步骤**

**Step 1：统一现有 Sketch 组件出口**

- 将现有 `SketchBorder`、`SketchDivider`、`SketchButton`、`SketchCard`、`SketchProgress` 等组件归档并规范导出。

**Step 2：统一设计令牌**

- 将 roughness、strokeWidth、bowing 等参数集中到设计系统令牌中。
- 页面级手绘风格尽量复用统一参数，而不是组件内随机散落。

**Step 3：renderer 替换延后评估**

- 是否引入新的 React renderer，放到后续专项评估中处理。
- 本阶段只以现有 roughjs 方案做收口，不新增底层依赖作为阻塞项。

**难度预估**

- 简单到中等（2-4 人天）

**文件落点建议**

- `xuejian/src/components/ui/`
- `xuejian/src/design-system/tokens.ts`


## 六、优先级路线图与工作分解

本次重排后的核心原则是：**先闭环、先安全、先收敛现有能力，再扩展高级功能**。

### 里程碑 1：“真实闭环 + 安全补洞”（预计 12-16 人天）

**目标**

让用户稳定完成“文档上传 -> 卡片生成 -> 卡片复习 -> 基础问答”的主流程，并补齐当前最明显的安全缺陷。

| 交付项 | 对应功能 | 说明 | 优先级 |
|--------|---------|------|--------|
| Stronghold / SecretStore 安全重构 | BYOK | Argon2 初始化、vault 解锁态、明文边界收紧 | P0 |
| PDF 解析分流 + 语义分块 + 卡片 Schema 校验 | 卡片生成 | 保留审核流，补齐质量与来源约束 | P0 |
| FSRS 每日调度队列 + 复习入口 | 复习系统 | 先完成可用学习闭环 | P0 |
| RAG 引用强制与答案降级 | 问答 | 稳定 citation 契约与回退行为 | P0 |
| 最小可用的 PDF-卡片联动 | 阅读/卡片 | 页码跳转、高亮联动、基础可用 | P0 |

### 里程碑 2：“现有 AI 能力增强”（预计 10-15 人天）

**目标**

在不重构主架构的前提下，增强现有问答、播客、动画体验。

## 七、测试与验收口径

### 7.0 M1 验收原则

里程碑 1 的验收采用“是否形成稳定闭环”和“是否消除阻塞风险”两条主线判断，不以功能数量为准。

M1 通过的最低条件如下：

- 用户可以在一个新安装环境中完成：配置模型 -> 导入文档 -> 生成候选卡片 -> 审核入库 -> 进入复习队列 -> 发起一次带引用的基础问答。
- 所有涉及 API Key 的常规前端查询、列表和日志输出中都不会出现明文密钥。
- 在 provider、embedding 或 GraphRAG 任一依赖失效时，系统仍能给出可解释的降级结果，而不是直接中断主流程。
- PDF 解析、卡片来源页绑定和问答 citation 至少在“原生文本 PDF”场景下稳定可用；扫描 PDF 和混合 PDF 至少达到可检测、可回退、可提示。

### 7.1 安全回归

- Stronghold 初始化、存储、删除、重启后恢复
- 配置列表接口不返回明文 key
- 连接测试成功/失败后 `key_status` 一致
- 宿主内部注入密钥成功，前端侧无明文持久化

**细化验收标准**

- 首次启动时：
  - 若本地尚无 vault，系统能完成初始化流程，不生成硬编码默认密钥。
  - 若初始化失败，前端收到明确错误提示，且不会留下半初始化状态。
- 已有 vault 再次启动时：
  - 未解锁状态下，前端可看到配置元数据，但无法获取明文 key。
  - 解锁后可正常进行连接测试和工作流调用。
- `storeApiKey` 调用后：
  - 配置列表中 `hasStoredKey=true`。
  - 前端不会收到明文 key 回显。
  - 重启应用后该 key 仍可用于宿主内部调用。
- `deleteApiKey` 调用后：
  - 配置列表中 `hasStoredKey=false` 或 `keyStatus=none`。
  - 重启应用后旧密钥不可再被宿主取用。
- 连接测试：
  - 成功时写入 `keyStatus=verified` 和 `keyVerifiedAt`。
  - 因认证失败而失败时，状态不会仍然保留为 `verified`。
  - 因网络失败而失败时，错误信息与认证失败可区分。
- 日志与接口：
  - 配置列表接口、错误提示、结构化日志中都不包含 API Key 明文。
  - 任意 UI 查询都不能把宿主中的密钥重新反序列化到前端 store。

### 7.2 文档解析与卡片生成

- 原生文本 PDF、扫描 PDF、混合 PDF 三类输入
- 分块保留 `pageStart/pageEnd/hierarchyPath`
- schema 校验能拒绝非法或无来源绑定的卡片
- 候选卡片能回链到 chunk/page

**细化验收标准**

- 原生文本 PDF：
  - 解析流程默认走文本提取主路径，不额外触发 OCR。
  - 至少能生成 section、chunk、page 边界信息。
  - 候选卡片可回链到 `chunkId` 和页码。
- 扫描 PDF：
  - 系统能识别“缺少文本层”的事实。
  - 若 OCR 可用，进入 OCR 路径并产出可用 chunk。
  - 若 OCR 不可用，前端收到明确提示，文档不会被错误标记为已完成结构化解析。
- 混合 PDF：
  - 系统能识别“部分页有文本、部分页无文本”的情况，或至少以保守方式整体降级。
  - 不允许把空白页或未识别页静默当作成功处理。
- 语义分块：
  - 每个 chunk 至少包含 `content`、`pageStart/pageEnd`、`hierarchyPath`。
  - 标题切换、长段落拆分、表格附近内容不会全部坍缩成单一巨块。
  - 分块结果在同一输入下应基本稳定，不因非功能性波动频繁变化。
- 卡片 schema 校验：
  - 非 JSON、缺字段、空字符串、缺来源绑定的输出会被拒绝，不进入候选列表。
  - 被拒绝的输出会记录为失败原因或质量过滤原因，而不是静默丢弃。
- 候选卡片质量：
  - 每张候选卡片至少能定位到来源 chunk。
  - 至少在原生文本 PDF 场景下，点击候选卡片可跳转到对应 PDF 页。
  - 当模型输出质量不足时，系统返回“生成失败/质量不足”，而不是生成不可审核的僵尸卡片。

### 7.3 RAG

- `hybrid search`、GraphRAG 不可用时回退到 FTS5
- 有答案时 citation 完整
- 无足够依据时返回 no-answer / excerpt fallback

**细化验收标准**

- 正常路径：
  - 当 embedding profile、hybrid search、provider 均可用时，问答返回 `answer` 与 citation 列表。
  - citation 至少包含 `chunkId`、`documentId`、`page` 或可等价映射到页码的信息。
- Hybrid 降级：
  - 当 embedding profile 缺失或向量检索失败时，系统自动回退到 FTS5。
  - 前端或调试信息中可识别当前 retrieval mode，便于排查。
- GraphRAG 降级：
  - 当 `graph_rag_search` 不可用时，不影响基础问答完成。
  - GraphRAG 失败不会让最终回答结构缺失 citation 字段。
- 无依据回答控制：
  - 未检索到有效 chunk 时，返回明确 no-answer / no-relevant-content，而不是模型自由发挥。
  - provider 不可用时，允许退化为 excerpt fallback，但必须带来源片段。
- citation 完整性：
  - 模型即使返回不完整 citation，后端也会过滤或补齐最小字段。
  - citation 不允许引用本轮未参与检索的 chunk。
- 前端联动：
  - 点击 citation 至少能打开对应文档并跳到相关页。
  - 若某条 citation 只有 chunk 级信息而无更精确锚点，也必须能回退到页级跳转。

### 7.4 现有功能防回归

- podcast 创建、审阅、重试
- animation 生成、失败回退、前端预览
- FSRS 调度结果与现有参数一致

**细化验收标准**

- podcast：
  - 现有创建播客流程不因文档整改而失效。
  - 脚本审阅的接受、编辑、拒绝三条路径仍能完成。
  - 重试后不会产生脏状态或历史段音频残留导致的新失败。
- animation：
  - 现有动画生成入口仍可用。
  - provider 失败时仍能回退到规则脚本。
  - 前端预览对 `queued/generating/ready/failed` 四类状态展示正常。
- FSRS：
  - 同一输入卡片与评分序列下，调度结果不因本轮整改产生非预期漂移。
  - 每日复习队列能稳定生成，且不会把未到期卡片错误放入当日主队列。
  - 当没有待复习卡片时，前端能给出明确空态。

### 7.4.1 PDF-卡片联动最小验收

该能力属于 M1 闭环的一部分，单独列出最小通过标准：

- 在候选卡片或正式卡片中点击“查看来源”后，应用能打开对应文档。
- 应用至少能跳转到来源页；若已有锚点信息，则优先高亮对应片段。
- 当精确锚点失效时，系统退回到页级定位，不直接报错中断。
- 当来源文档已删除或不可访问时，前端显示可解释错误，不崩溃。

### 7.5 性能与阈值

- 先基于真实数据量做 sqlite-vec 查询压测
- 根据结果再决定监控阈值与 LanceDB 迁移时机

**细化验收标准**

- 至少记录向量条目数、检索耗时、P95 延迟和设备环境。
- 不以单机一次测试结果直接写死统一阈值。
- 若当前数据规模下性能可接受，则 M1/M2 不引入 LanceDB 改造。
- 若性能不可接受，先输出压测结论和瓶颈归因，再决定是否进入接口抽象阶段。


## 八、外部事实核验与文档口径

以下结论已经用于本次修订：

- Docling 官方文档确认 OCR 配置可选 Tesseract、EasyOCR、RapidOCR 等能力。  
  参考：<https://docling-project.github.io/docling/reference/pipeline_options/>

- Tauri Stronghold 官方文档推荐使用 Argon2 派生 Stronghold 所需 32-byte key material。  
  参考：<https://v2.tauri.app/es/plugin/stronghold/>

- sqlite-vec 当前是 `vec0` / 手动 KNN 路线，适合本地嵌入式混合检索，但不应被表述为 ANN 引擎。  
  参考：<https://alexgarcia.xyz/sqlite-vec/features/knn.html>

- LanceDB 官方文档确认其提供 Python、TypeScript/Node.js、Rust 的正式支持，并主推索引能力。  
  参考：<https://docs.lancedb.com/api-reference>  
  参考：<https://docs.lancedb.com/indexing>

- Microsoft GraphRAG 官方文档确认 local / global 是不同查询模式，global search 依赖 community reports。  
  参考：<https://microsoft.github.io/graphrag/query/global_search/>

- Web Speech `SpeechSynthesis` 在浏览器层面广泛可用，但桌面 Tauri 仍受底层 WebView 与系统语音包影响，因此只能写成“尽力回退”，不能写成稳定离线承诺。  
  参考：<https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesis>

以下内容未充分核实，统一降级为候选技术或待评估路线：

- `manim-mcp-server` 的近期维护活跃度判断
- `react-rough-fiber` 是否应作为未来 renderer 替换方向


## 九、最终结论

本次修订后的执行基线是：

- **M1 只做闭环与安全补洞，不做技术扩张。**
- **问答、播客、动画按“增强现有实现”处理，不再按“从零建设”描述。**
- **sqlite-vec、roughjs、现有 workflow 架构继续保留，先收敛，再评估替换。**
- **所有新增设计都优先服从现有代码真相、前后端契约稳定性和本地优先安全边界。**
