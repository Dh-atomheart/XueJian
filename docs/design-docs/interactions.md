# 跨页交互与状态反馈规范

## 1. 目标

本文件定义跨页面共享的交互语言，确保用户在上传、阅读、学习、配置和长任务处理中获得一致反馈。

## 2. 导航规则

全局主路径固定为：

`Dashboard -> Library -> Reader -> Review -> Settings`

规则：

- `SidebarRail` 负责一级导航
- `TopBar` 负责当前页面上下文，不负责站点级导航
- 当前页面提示应稳定、弱干扰，不依赖高饱和颜色

## 3. 上传与卡片生成流程

## 3.1 上传流程

推荐交互节奏：

1. 用户选择 PDF
2. 文档立即进入列表，并显示 `uploading / parsing`
3. 解析完成后显示 `indexing / generating`
4. 完成后进入 `ready`
5. 出错时进入 `error` 并给出重试动作

反馈要求：

- 始终告诉用户“现在在做哪一步”
- 用阶段文案替代笼统的“处理中”
- 不在处理中反复打断用户

## 3.2 卡片候选确认流

适用场景：LLM 生成候选卡片后，用户进入确认或编辑阶段。

规则：

- 候选卡片必须区分“未确认”和“正式卡片”
- 批量接受、单张编辑、单张删除三个动作都应清晰存在
- 编辑行为不能丢失来源锚点和上下文信息

推荐反馈：

- 保存成功：轻量行内反馈
- 批量确认完成：列表顶部摘要提示
- 冲突或失败：保留原内容并提示用户重试

## 4. 阅读联动

阅读页是 MVP 最核心的交互场景，规则必须最严格。

### 4.1 原文到卡片

- 选中文本后出现轻量创建入口
- 创建入口应靠近选区，但不能挡住正文
- 创建完成后，新卡片进入当前页上下文区

### 4.2 卡片到原文

- 点击卡片时，PDF 定位到对应位置
- 原文高亮应使用浅色、短时过渡
- 跳转后应保留上下文感，让用户知道为什么到这里

### 4.3 联动反馈

- 高亮持续时间足够让人看清，但不应长期停留造成污染
- 同步定位失败时，文案应说明是否可按页回退或手动查看

## 5. 学习节奏

## 5.1 进入学习

- 进入学习页后，优先显示当前卡片，不先展示统计解释
- 若今日无卡片，页面重点改为“今日已完成”

## 5.2 翻卡

- 翻卡动效应服务“正面 -> 答案”的理解转换
- 不使用夸张三维效果或迟滞过长的动画

## 5.3 评分

- `Again / Hard / Good / Easy` 必须同时依赖文字和位置表达差异
- 提交后尽快进入下一张，减少停顿
- 若提交失败，应允许就地重试，不把用户踢出学习流

## 6. 设置与连接测试

规则：

- 输入配置后，保存和测试连接是两个清晰动作
- 测试连接时应显示处理中状态，避免用户重复点击
- 成功反馈靠近表单出现，失败反馈说明可能原因

推荐错误文案包含：

- API Key 无效
- Base URL 不可达
- 模型名不可用
- 网络或供应商错误

## 7. 长任务与异步反馈

适用任务：

- 卡片生成
- 文档解析
- 连接测试
- 恢复中断任务
- 预算提示与超限阻断

统一反馈模型：

- `idle`
- `loading`
- `processing`
- `success`
- `error`
- `recoverable`

规则：

- `loading` 用于等待初始数据
- `processing` 用于用户已发起且后台仍在执行的任务
- `recoverable` 用于中断后可继续的长任务
- 长任务提示优先行内或页面内嵌，不默认使用模态阻塞

## 8. 提示语言

文案应该像一个清晰的学习工具，而不是拟人化助手。

建议：

- 先说事实：`正在解析 PDF`
- 再说结果预期：`完成后会生成卡片候选`
- 最后说动作：`你可以先继续浏览其他文档`

避免：

- 模糊文案，如“请稍等”“正在努力中”
- 过度拟人化文案，如“我来帮你想想”
- 只报错不提供下一步

## 9. 可访问性交互底线

- 所有关键按钮必须可键盘访问
- 焦点态不可被纹理和装饰覆盖
- 状态提示不能只用颜色区分
- 长任务状态变化应能被清晰感知，不依赖细微动画
